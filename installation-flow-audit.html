Context

How a booking becomes an installation task

When a booking is verified, the system creates a connection, finds the best CSP (DAS), and creates an installation task (TAS). The CSP is then notified and must respond — propose a slot (happy case) or decline (reallocation). If they do neither within P41 = 2 working hours, the booking is taken back and sent to a different CSP.

Read of the scorecard

Everything up to task creation is clean — connection creation, DAS assignment and TAS task creation all run at 99.8–100%. The P41 timer itself is also healthy: 99.3% of eligible tasks correctly get timed out when the window lapses, so enforcement is not the problem. The funnel breaks in exactly two places: notification delivery (PN 83.9%, FPN 64.6% — both L1 metrics that should be ~100%) and CSP response behavior (only 60% of CSPs who open a task act on it).

Fix track A · attention & delivery (L1)

Make sure every task reliably reaches the CSP

Target: PN and FPN delivery back to ~100%-class health, and the missing Task Attention Rate measured. This track caps the "never opened" third of timeouts (15.7pp).

A1Move notification triggering from CleverTap to Firebase direct
Both delivery gaps (PN 83.9%, FPN 64.6%) share the same trigger path via CleverTap. Triggering through Firebase directly removes an intermediary hop and its failure modes. Already identified as the fix in the metrics sheet; needs an owner and a date.
Targets: PN Delivery 83.9% → ~98% · FPN Delivery 64.6% → ~95%
A2Fix the FPN render pipeline's silent failures in the partner app
A code-level audit of the partner app (Apr 2026, release 3.7.7) found four compounding bugs where an FPN is delivered to the device but never rendered — each failing silently, with no event emitted:
  • a fixed 1.5s cold-start delay before invoking the FPN screen, while real cold start on mid-range devices is 3–4s;
  • if the app engine isn't ready at that moment, the code logs an error and gives up — no retry, no fallback;
  • the messaging service declares success if the app process is merely in the foreground — "process alive" ≠ "FPN rendered";
  • a payload parsing failure exits silently.
Fix: replace the fixed timer with an engine-ready callback, add retry + fallback when the engine isn't ready, and only count success when the FPN screen confirms it rendered.
Evidence: fpn_drop_analysis (Apr 2026) — bugs verified in CustomFirebaseMessagingService.kt / MainActivity.kt on master; re-verify against the current release before build.
Targets: FPN delivered → rendered gap closed; every failure path emits a diagnostic event
A3Harden the FPN mechanism itself
Promote the full-screen intent to the primary FPN channel (today it's a lower-tier fallback), and add OEM-specific push SDKs for the device brands where background delivery is throttled (Xiaomi / OPPO are the largest offenders in the delivery data).
Target: FPN delivery resilient on aggressive-battery-management OEMs
A4Add a multi-channel fallback ladder for attention
Today attention is a single shot: PN + FPN at task creation, fanned to Manager, Manager+ and Owner. If none of those deliver or get opened within a defined window (e.g. 15–20 min), escalate automatically:
  • re-trigger PN + FPN;
  • then an automated IVR call to the CSP;
  • then SMS / WhatsApp with a deep link to the task;
Each rung fires only if the task is still unopened, so well-behaved CSPs never see the escalation.
Target: Task Open Rate 84.3% → 95%+
A5Instrument the Task Attention Rate (currently unmeasured)
The combined "did anything reach any of the three recipients" metric is blank in the scorecard — we cannot manage what we don't measure. Define it as: tasks where ≥1 of {PN, FPN} delivered to ≥1 recipient ÷ tasks created, and add per-channel delivery telemetry at every failure point found in A2.
Target: Task Attention Rate on the dashboard, daily, with D-1 comparison
Fix track B · response behavior (L2)

Convert attention into a response

The bigger lever: 33.7 of every 100 tasks are opened and then abandoned. These CSPs saw the task. The fixes below make the deadline visible, make declining cheap, and make silence costly.

B1Show the P41 deadline as a live countdown
Today the 2-working-hour window is invisible to the CSP — nothing in the task or home feed says "this booking leaves you in 1h 40m." Add a live countdown on the home feed and task card, computed from the actual working-hours-projected P41 fire time (so an evening task correctly shows tomorrow-morning expiry, not a naive 2-hour clock). A deadline that can be seen is a deadline that changes behavior.
The reallocation trigger time already exists in the scheduler; what's new is exposing it to the app (specced in SCHED-01).
B2Escalating nudge cascade inside the P41 window
A slot-proposal urgency nudge already fires at 1 hour and bumps the task's attention state. Extend it into a cascade: nudge at 1h → countdown intensifies → final warning to Manager+ and Owner shortly before expiry ("this booking will be reassigned in 20 minutes"). Every fire is logged, so we can measure which rung actually converts.
Target: Response Rate 60% → 75%
B3Make declining explicit and low-friction
Timeouts outnumber declines ~3:1 (49.4% vs 17.2% of opens). For many CSPs, silence is just the lazy decline — and it costs the customer 2 working hours of waiting versus minutes for an explicit decline. Put a prominent "Can't take this" action with a mandatory structured reason (too far / no capacity / slot conflict) on the task. Every converted silent-timeout → explicit-decline is a directly faster reallocation and gives us the reason data we currently don't have.
Target: shift 10–15pp from timeout into decline; reallocation latency drops from 2 working hours to minutes for that share
B4Make silence visibly costly — consequence symmetry
The system already scores a P41 timeout like a decline pattern (cooldown P51, assignment counters) — but the CSP never sees this. Surface it: show timeout counts on the CSP's own quality view, and feed responsiveness into allocation priority so fast responders demonstrably get more bookings. Behavior follows what's measured and shown.
B5Find out why opened tasks are abandoned
33.7pp is too large to fix blind. Two quick studies: (1) segment the open-but-silent cohort by CSP, geography, time-of-day and task age — is this concentrated in a few chronically unresponsive CSPs or spread thin? (2) call 20–30 CSPs who opened and didn't respond within a day of the event and ask why. The structured decline reasons from B3 then keep this signal flowing permanently.
Data gaps & asks

What we still can't see

  • Task Attention Rate — the combined delivery metric is not instrumented (fix A5).
  • D-1 values for PN/FPN delivery, open, response, decline, timeout and slot-proposed rates — day-over-day trend view is incomplete in the source sheet; being backfilled.
  • Decline/abandon reasons — no structured reason data exists for either declines or silent timeouts (fix B3).
  • Per-recipient delivery split — PN/FPN delivery is not broken down by Manager vs Manager+ vs Owner, so we don't know if any recipient reliably receives anything.

Asks from this review: (1) prioritize the Firebase migration (A1) and FPN render fixes (A2) with app-release owners; (2) approve the countdown + nudge cascade (B1/B2) for the next sprint; (3) sponsor the abandonment study (B5) so Track B targets are grounded in reasons, not guesses.
